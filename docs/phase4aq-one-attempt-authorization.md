# Phase 4AQ — One-attempt operator authorization validation

Phase 4AQ validates, but never creates, an externally supplied authorization artifact for exactly
one disposable simulation attempt. A valid result does not authorize production execution,
exchange access, paper/live orders, or any service action.

## External artifact contract

`phase4aq.one-attempt-operator-authorization.v1` must declare that it was externally supplied and
not generated by guarded tooling. Its canonical hash binds:

- the exact Phase 4AK readiness-envelope hash;
- the sorted, duplicate-free set of exact readiness-row hashes;
- the exact successful Phase 4AL simulation-report hash and readiness lineage;
- the canonical production-database identity hash recorded by Phase 4AK;
- the exact offline executor build-identity hash supplied to the validator;
- one non-empty attempt identifier;
- one non-empty operator identity and optional distinct second reviewer;
- a timezone-aware authorization deadline no later than Phase 4AK's approval deadline; and
- explicit non-revocation and disposable-only scope.

The artifact must set exchange, order, paper-order, and production-execution authorization false.
Any prohibited true scope fails closed.

## Validation behavior

Hash/schema/timestamp corruption raises a stable `PHASE4AQ_` error. Semantically well-formed but
unacceptable artifacts produce sorted refusal reasons. Expiration uses `now >= expires_at`; equality
is expired. An attempt identifier already present in externally supplied history is refused, and a
duplicated history is itself invalid.

The validator hashes operator identities in its output rather than reproducing their raw values. It
does not store credentials, signatures, SQL, callbacks, or executable authority.

## Outputs

Paired publication produces:

- `phase4aq.authorization-validation.v1`; and
- `phase4aq.authorization-refusal-manifest.v1`.

`authorization_valid_for_disposable_test_attempt=true` means only that the external artifact is
valid for one later sandbox attempt. `authorization_valid_for_production` and
`execution_authorized` always remain false. The refusal manifest explicitly states that the
validator did not generate authorization and that exchange/order authorization is absent.

No Phase 4AQ command accesses a database, acquires a lock, contacts an exchange, creates an order,
or controls a service.
